## 2. 当前架构

```text
┌──────────────────────────────────────────────────────────────┐
│ packetsage-desktop.exe（Tauri 外壳 · Rust · 4.5 MB）           │
│  · SidecarManager：两个子进程的生命周期、读写、EOF 感知        │
│  · 命令面：analyze / task_overview / run_agent / cancel / …    │
│  · WebView2：React + TS + Vite + Tailwind 前端                 │
└──────┬────────────────────────────────────┬──────────────────┘
       │ 通道 A：stdio JSONL（收口 §5.4，已冻结）│ 通道 B：stdio JSONL（§4.5，本版冻结）
       ▼                                    ▼
┌───────────────────────┐        ┌──────────────────────────┐
│ packetsage serve      │        │ packetsage-agent serve    │
│ （引擎 · 125 MB 未 strip）│◄──────┤ （PyInstaller onedir · 67 MB）│
│  解析/规则/重组/tc 台账 │ 又一份 │ 工具循环/预算/provider/报告   │
└──────────┬────────────┘ 引擎   └──────────────────────────┘
           │ sqlx
           ▼
      SQLite（唯一真相源）
```

三点必须知道的**现状事实**：

1. **进度是"两个引擎进程"**：外壳起一份引擎，Agent 自己又起一份（`PACKETSAGE_ENGINE` 注入）。
   文档 §2.2 的期望是"一个引擎、两个客户端"。实测：只起外壳时 1 个 `packetsage.exe`，
   把 Agent 也起来后 **2 个** [实测]。
2. **证据路径不经过 Python**：摘要、会话、告警、finding、台账全部由外壳直连引擎（通道 A）；
   Python 只负责 run 与报告（通道 B）。
3. **数据都在 app data**：`%LOCALAPPDATA%\PacketSage\{packetsage.db, reports\, logs\}`；
   provider 凭据**尚未**进 Windows 凭据管理器（U7 未做，现在靠环境变量注入）。

## 7. 架构评估：HTTP / MCP / in-process 值不值得做

### 7.1 拆成三件独立的事

| 提法 | 现状 | 结论 |
|---|---|---|
| 两个核心分开运行 | **已经是**（Rust 引擎 / Python Agent 各自进程） | 保留：故障隔离 + 语言边界是资产 |
| 引擎链进 Tauri（in-process） | 现在同语言但不同进程 | 有收益有代价，见 7.2 |
| 开 HTTP 端口 / 包成 MCP 连 Python | 现在 stdio JSONL（通道 A/B） | 要慎重，与 §4.2/§2.3/§2.4 三条已成文决定冲突 |

### 7.2 四个选项

| 选项 | 收益 | 代价 | 成本 |
|---|---|---|---|
| **A. 引擎链进外壳**（in-process） | 省 125 MB 二进制与一个进程；通道 A 序列化归零（本来就是零头） | **丢故障隔离**（core panic = 整个应用崩；且外壳 release 是 `panic = "abort"`，`catch_unwind` 也救不回）；core 多一个消费者 → API 稳定性负担翻倍；必须先"抽库共用" | 1–2 周 |
| **B. 本地 HTTP（+token）** | Agent 不再自起引擎 → 回到"一个引擎两个客户端"；顺带获得 curl/notebook 集成面 | §4.2 的四条理由全部重新承担（本地任意进程可连、端口冲突、防火墙观感、崩溃感知退化）；**并发不会凭空出现**（`Worker` 是 `&mut self` 单所有者）；等于再冻结一遍 §4.5 规模的协议 | 1–2 周 |
| **C. MCP 适配器** | 外部客户端（Claude Desktop/Cursor）可用引擎工具 | §2.4 明文"不做 MCP"；`tools/list` 会把 9 个工具**再声明一遍**（漂移）；MCP 是"客户端 spawn 服务端"→ 两客户端=两服务端进程，又回到 P3，除非走 MCP 的 HTTP transport | ~1 周 |
| **D. 命名管道 / 本机 socket（沿用 §5.4 帧）** | 同样拿到"一个引擎两个客户端"；无端口无防火墙、可绑 owner-only ACL、**不引入新语义** | 需要给 Python sidecar 一条 `--engine-pipe`；协议快照要同步（帧不变，传输变） | 3–5 天 |

### 7.3 抽库这件事是所有方案的前置（也正是文档自己写的路）

《GUI 工程规格书 v0.2》§2.3 的原话：要做得先"把 `serve` 的逻辑抽成库，CLI 与 GUI 共用"。
现状对这条路很友好：

* `crates/packetsage-cli/src/serve.rs` 的 `Worker<W: Write>` 已经是"无 IO 的状态机 +
  `dispatch(&RpcRequest) -> RpcResponse`"，`run(loaded)` 只是 stdin/stdout 适配器；
* `packetsage-cli` 现在**只有 `main.rs`、没有 lib target** → 加一个 lib target 就能把
  `Worker` 暴露给外壳（或独立成 `packetsage-serve-lib` crate）；
* 判据明确：`exit_codes.py` 43 条 + `gui_contract.py` 7 条必须全绿才算没回归。

### 7.4 我的建议路线

1. **先抽库**（1–2 天，零语义改动，可整条回退）；
2. 要"一个引擎"就选 **D（命名管道）**——它只换传输不换语义，也不碰 §4.2 的取舍逻辑；
3. **in-process 与 HTTP 都先不做**：A 的账（丢隔离 vs 省体积）建议等 D3 的 strip 做完再算，
   B 只在"真要给外部工具用"时才做；
4. **MCP 单独排期**，作为对外适配器复用同一个 `Worker`；要做先改 §2.4 并写 ADR。

## 14. 第四轮：提速（先测再改 → 削步数）

**一句话**：慢的不是工具，是**串行的 LLM 往返**——工具总耗时 **10 ms** 量级，
其余全在模型往返上。所以先量、再削往返次数、再让每次往返吃到缓存。
完整数据与口径见 `docs/agent-latency.md`。

### 14.1 先测（#1）

`llm_ms`（`provider.decide` 的墙钟）与 `tool_ms`（引擎 `duration_ms`）分开累计：

* `llm_round` 事件加 `llm_ms` / `tool_ms` / `preloaded` 三列（§4.5 **只增字段**，
  快照已同步更新，S70 通过）；
* 每条台账行带 `llm_ms`：这次调用是等了多久的模型才发出来的；
* 界面：「调查过程 · 9 步 · 8 次工具调用（另有 4 次引擎预取）· … · 12.4 s 模型 / 0.01 s 工具」，
  调查进行中时结论卡上也实时显示这个拆分。

不先做这层，就会出现"把慢数据库当成慢模型"的经典误判。

### 14.2 实测（本机，模拟 TTFT，`agent/tests/bench_roundtrips.py --ttft 1.5`）

| 方案 | 模型往返 | 步数 | 工具调用 | 模型耗时 | 工具耗时 | 墙钟 |
|---|---:|---:|---:|---:|---:|---:|
| 探索式（现状） | 9 | 9 | 8 | 13500 ms | **10 ms** | 13571 ms |
| 预取式（改后） | **4** | 4 | 3 | 6000 ms | 13 ms | **6075 ms（−55%）** |

两组都拿到 2 条结论；`E1–E6` mock 复测 **6/6 ok**、`path_match 1.00`、`forged_refs 0`
（预取没有削弱反幻觉：事实块里带真 `tc_*` 锚点，模型引用它们本来就合规）。

**口径**：这里的 `ttft` 是模拟值，绝对值没有意义；有意义的是**往返次数的乘数**——
真实 provider 下墙钟 ≈ 往返次数 ×（TTFT + 输出）。真 key 的复测还没跑（要预算）。

### 14.3 改了什么

| # | 改动 | 位置 |
|---|---|---|
| 2 | **预取确定性事实**：第一次模型往返之前就取回摘要 / 规则告警 / 协议统计 / Top 会话（同一批工具、同一本台账、真 `tc_*` 锚点），写进第一条消息——模型从"分析"起步 | `preload.py` + `agent.py::run` |
| 3 | **一轮多工具**：模型同一轮请求的多个工具全部执行（原来只跑第一个，其余的悄悄丢掉） | `provider.py::Decision.calls`、`agent.py::_run_tool` |
| 4 | **缓存友好**：system prompt / 工具清单 / 预取事实 / goal / 收尾格式全部进**第一条**消息。原来 `FINALIZE_INSTRUCTION` 挂在尾部，等于每轮都让前缀缓存从第 3 条消息起全部失效 | `provider.py::decide` |
| 5 | 两阶段观感：结论在 run 进行中逐条落到结论卡（上一轮已做），报告仍是按需动作 | `desktop/src/App.tsx` |

### 14.4 还没做

* **真 key 的 E1–E6**：验证两件事——往返次数真降到 3–4，以及去掉尾部收尾提醒后模型仍会收尾。需要你点头（花预算、抓包内容会发给 provider；样本是合成的 `samples/synth-mixed.pcap`，不含隐私）。
* **流式输出（`stream=True`）**：把 TTFT 变成看得见的字，感知延迟再降一档；要改 provider 的解析路径（流式 + function calling），单独排期。
