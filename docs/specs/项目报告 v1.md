## 5. 本轮新发现的缺陷（都有证据，按严重度排）

### 5.1 F1 · 预取的工具调用没有进 `result.trace`，两条读数路径分叉了 【中】

**现象**：`python tests/gui/app_cases.py` 的 S58 失败，判据是
“实时 trace 的最终条数与 `result.trace` 不一致”；连跑两次结果相同 [实测 09-23]。

**根因**（读代码确认，不是猜）：`agent.py` 的预取分支里，每条预取记录只做了三件事——
`policy.state.traces.append(entry)`、`trace_payload.append(entry)`、发 `tool_call_finished` 事件；
**唯独没有 `result.trace.append(...)`**。而正常工具路径（`agent.py` 里 `_run_tool` 的收尾处）是会 append 的。

于是同一个 run 有了两个工具条数：

* 界面/原型读 `policy.state.traces` → 含 4 条预取；
* `result.trace` → 不含预取，而 `eval/run_eval.py` 的 `tools / steps / tool_calls` 三个指标都从这里算。

**影响**：

1. 冻结的 Streamlit 套件 1 项红，**而这条套件在 CI 里真跑**（`.github/workflows/ci.yml` 的
   `GUI interface cases S57-S65` 步骤）→ 仓库一旦推送，CI 就是红的；
2. `run_eval.py` 报出来的工具路径比实际发生的少 4 条（E1 只列 `get_capture_summary, get_conversations`，
   而那次 run 实际还做了 4 次预取）；
3. 这正是项目核心不变量（“每个数字都能回溯到某次工具调用”）最怕的那类分叉。

**注意**：桌面应用本身读的是事件流，所以**界面上的数字是对的**——这条缺陷伤的是“两个消费者看到不同的账”。

**修法**：三行以内（预取分支补一次 `result.trace.append(...)`，或让两条路径共用同一份列表），
但要先定一件事：**预取到底算不算“模型这一步做的事”**——如果算，`run_eval` 的期望工具路径要一起改
（否则 E1–E6 的 `path_match` 会掉）。

### 5.2 F2 · 冻结原型与 Agent 的漂移没有回归网 【中】

F1 之所以能活到今天，是因为 9/21 的提速改动（预取 / 一轮多工具 / 流式）**只跑了 Python 单测与契约套件，
没跑原型套件**。报告 v0.1 在 §14 明确写了“E1–E6 mock 6/6 无回归”，但没提 `app_cases.py`。
原型已经冻结为“参考实现”，但它**仍然挂在 CI 上当门禁**——这是“冻结了却还在把关”的矛盾。

**两个选项，需要你选一个**：把原型套件修绿（改断言口径），或者把它从 CI 摘掉、只留 `docs` 里的历史记录。

### 5.3 F3 · 仓库还没有纳入版本控制 【中】

当前目录不是 git 仓库（`git log` → `fatal: not a git repository`）[实测 09-23]。
AGENTS.md 允许 `git init`（但不允许任何远程写入）。没有版本控制意味着：

* 没人能说清“09-22 那批改动到底动了哪些文件”（本报告的 §4 是我按文件 mtime 反推的）；

## 10. 结论

* **代码层面**：这个项目的骨干是真的完工了——三层冻结契约、175 + 179 + 43 + 7 + 8 + 22 项自动化用例、
  十步主线可复现、桌面应用有真机截图。**没有“看起来做完了其实没有”的部分**（除了 F1 那一处分叉）。
* **交付层面**：**一次人工验收都没做过**，安装器的三个收尾动作没做，CI 是红的。
  换句话说，“能演示”和“能交付”之间还隔着一段**主要是人力与机器环境、而不是工程量**的距离。
* **最短路径**：先花半天把 B1 做完（修 F1、定 D5、建 git），把 CI 变绿；
  然后你在一台干净 VM 上按 §8.2 走 M1–M24——**那 24 条走完的那一刻，这个项目才算完成**。
