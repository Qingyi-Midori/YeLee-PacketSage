## 1. 正在流的那段正文，是收尾信封的**原文**（本轮最主要的一条）

**现象**：一轮跑着的时候，结论卡里"模型正在写的那段话"是这么一副样子——

```text
{"summary": "这份抓包里的 **DNS 查询** 集中在同一台主机上。\n\n## 关键发现\n\n- `S-000003` 在 11:02–11:07 之间发了 12 次查询\n- 其中 3 次指向 `ns1.example.net`\n\n| 会话 | 包数 | 方向 |\n|---|---|---|\n…", "findings": [{"title": "DNS 查询集中", "severity": "info", …
```

——大括号、`\n` 两个字面字符、`findings` 数组全在正文里；Markdown 的标题、列表、表格
被 `\n`（不是换行，是**反斜杠 + n**）压成一整行。同一段正文，收尾之后 sidecar 把它解析
出来，结论卡立刻就干净了：**前后两副面孔**。

**根因（两层）**：

* 协议这一层是对的：`llm_delta` 的 `content` 通道发出去的**就是模型原文**
  （`provider._read_stream()` 把 SSE 的 content 片段原样交给界面），而 run / chat 两套
  收尾指令都要求模型用 `{"summary": …, "findings": […]}` 信封作答（`prompts.py`）。
* 界面这一层漏了一步：`App.tsx` 的 `liveDraft` 直接取最后一条 content delta 的 `text`
  就交给 `MarkdownView`，**没有做 sidecar 收尾时做的那件事**（取人话、解转义）。

**修法**：新增 `desktop/src/envelope.ts`（纯逻辑，不碰 React / Tauri），`liveDraft` 先过
`humanDraft()`：

* 取 `summary` / `answer` / `text` 字段的值（模型常用的三个别名、方括号包着的写法、
  中英文冒号都认）；
* 值是 JSON 字符串时按字符串读到收尾引号——**流到一半（字符串还没闭合）也给到当前进度**，
  正好停在反斜杠上也不吞字符；
* 解 JSON 转义：`\n` `\r` `\t` `\"` `\\` `\/` `\uXXXX`（`\\n` 这种"转义过的反斜杠 + n"
  不会被误当成换行）；
* 信封把机器字段写在前面（`{"findings": […], "summary": "…"}`）时，按**括号深度**只在顶层
  找那个键——`findings` 里每条结论自己带的 `summary` 是第二层，不会被抓来当回答；
* **判据与服务端同一条：文本以信封开头才清理**，普通散文一个字都不动（免得把正常回答
  从中间截断）；
* 取不到人话（本轮只写 `findings` / 信封才开了个头 `{"summ`）时返回空串，界面照旧显示
  「正在追查…」——**不把半截 JSON 画到结论卡上**。

**口径对齐的证据**：拿 13 个样本（正常信封 / `answer` 与 `text` 别名 / ```` ```json ```` 围栏 /
`[summary]: "…"` 那种非法信封 / 无引号信封 / 散文反例 / 前后空白 / 引号与反斜杠 / `\t` / `\uXXXX`）
同时跑**服务端** `provider._salvage_summary()`（含 `_loads_json`、`_strip_code_fence` 那条路径）
与**前端** `humanDraft()`，逐条相等——流完时前端草稿就是服务端最终给出的那段人话。

**机器字段照旧不丢**：原文仍在时间线的「输出 · 原文」折叠项里（第 29 / 32 条），
本轮一个字没改。

## 2. 模型写的**短字段**露出 Markdown 记号

`FindingRow` 的两处文字都是**模型写的**（引擎库里的 `finding.title` 与 `finding.summary`），
但一处直接塞进 `<span>`、一处塞进 `<p>`——模型在标题里写 `**加粗**`、在原话里写反引号或
短列表时，用户看到的就是记号本身。修：

* 标题走新的 `MarkdownInline`（行内渲染：`p` / `ul` / `ol` 摊平、`li` 之间给个「·」分隔），
  标题在布局里是行内元素，**不引入第二套排版**；
* 原话走 `MarkdownView`，并用 `.finding-detail .md` 把它压回原来的小字号与紧凑（结论行里
  它是注解，不是第二段正文）。

## 3. `.md` 少了两种元素的规则：围栏代码块与有序列表

渲染器是好的（`react-markdown` + `remark-gfm` 在打包产物里），但样式表里 `.md` 只写了
`h1/h2/h3`、`p/li`、`ul`、`code`、`table`、`blockquote`：

* **围栏代码块**从没写过规则 → `pre > code` 吃到的是**行内 `code`** 那条（底色小块 + 边框 +
  左右 4px），一段两行的代码看起来是"一排小药丸"，长行还会直接顶破版心；
* **有序列表**从没写过规则 → `ol` 吃浏览器默认的 `padding-left: 40px`，而 `ul` 是 `1.2em`，
  同一段回答里「1.」比「•」深一截，看着像多了一级。

修：`pre` / `pre code` 有自己的块（`--panel` 底、`--line-soft` 边、6px 圆角、内边距、
横向滚动、12px 等宽、`white-space: pre`）；`ul` 与 `ol` 统一 `padding-left: 1.4em`；
`li + li` 2px；子列表不另起段间距；`a` 用**中性下划线**（不用状态蓝，第 9 条的色彩纪律）；
补 `hr`、`del`、GFM 任务列表的方块；`.md` 首尾不留空档。

## 4. 宽表格没人管横向溢出

`.md table` 是 `width: 100%`，而 `<table>` 自己不会滚：报告里六列的「主要会话」
（`endpoint_a` / `endpoint_b` / 方向 / 会话 / 包数 / 字节，长 IPv6）在右栏、或把窗口拉到
最小的 1000×640 时只能挤成一条条。修：`MarkdownView` 用 `components.table` 给表格套一层
`.md-table-wrap`（横向滚动壳），表格改 `width: max-content; min-width: 100%`，
单元格 `max-width: 34ch` + `overflow-wrap: anywhere`——窄表格照旧铺满，宽表格自己滚。

## 请在 4.1.5 上这样看（宽窄各一遍，最小 1000×640）

1. **跑一轮调查**（run）：跑到一半时盯结论卡——**应当看到和收尾后一样的排版**
   （加粗、`##` 标题、`-` 列表、表格都在渲染，没有大括号、没有 `\n`、没有 `findings`）。
   收尾那一刻文字不应该"换一副面孔"。
2. **追问一轮**（chat）：同上，回答正在写的时候就是渲染好的样子。
3. **一次贴满元素的回答**：粗体 / 行内代码 / 无序与有序列表 / 标题 / 表格 / 引用 / 代码块 /
   链接，在**聊天回答**与**右栏报告**两处各看一遍；代码块应该是一个带底色的块（不是一排小药丸），
   有序列表与无序列表左边缘应当对齐。
4. **把窗口拉到最小、并打开右栏报告**：六列的「主要会话」应当**自己横向滚**，不去顶破栏宽。
5. **点开时间线的「输出 · 原文」**：那里**仍然是原文**（含 JSON）——这是第 29 / 32 条有意的，
   不是漏修。
