# 1. 项目目标

## 1.1 核心目标

PacketSage 接收 PCAP / PCAPNG 文件，完成：

```text
捕获文件
  ↓
格式识别
  ↓
链路层解析
  ↓
网络层解析
  ↓
传输层解析
  ↓
应用层元数据解析
  ↓
TCP 流重组
  ↓
会话聚合
  ↓
规则检测
  ↓
Agent 按需取证
  ↓
分析报告
```

【设计】

项目的价值不在“把全部报文塞给 LLM”，而在于：

> **让传统解析器提供确定性证据，让 Agent 决定下一步取什么证据。**

---

## 1.2 第一版明确不解决的问题

MVP 不做：

- 实时抓包；
- TLS 解密；
- 完整 HTTP/2、HTTP/3 协议栈；
- 深度 DPI；
- 自动网络处置；
- 自动阻断；
- 多 Agent 协作；
- Web 前端。

【设计】

这些功能全部进入后续 roadmap，而不是第一版的验收标准。

---

# 2. 核心非功能要求

## 2.1 不崩溃原则

【设计】

单个坏包不允许导致整个任务崩溃。

允许：

```text
packet #1821
decode_error = truncated_ipv4_header
```

然后继续处理：

```text
packet #1822
packet #1823
...
```

但如果文件级结构损坏到无法继续定位下一条记录，则整个任务可失败。

---

## 2.2 结果可追溯

每一个重要发现必须能追溯到：

```text
task_id
↓
finding / alert
↓
rule_id 或 tool_call
↓
session_id / packet_index
↓
原始 capture
```

Agent 生成的自然语言不是证据本身。

---

## 2.3 默认保护 Payload

【设计】

默认工具只返回：

- header；
- metadata；
- 数量；
- 摘要；
- 有界长度的 printable preview。

只有显式请求：

```text
reconstruct_stream(...)
```

时才允许取得有限 Payload。

默认上限：

```text
single tool result: 8000 chars（≈ 8 KiB）
single reconstructed stream: 256 KiB（不变）
```

【设计】【v0.3】

- 64 KiB → **8000 chars**：数值由《M3～M6 工程规格书 v0.2》§4.3 `ToolSpec.max_result_chars` 取代本节——超限时走结构化摘要（保数值字段与排序头部，丢弃 preview 正文），见该规格 §4.3 `wrap_result`；
- 256 KiB 流上限不变（与 §14.2 `reconstruct_stream` 的 `max_bytes ≤ 262144` 一致）；
- §24 `agent.max_payload_bytes: 65536` 是 **payload preview 的字节上限**，与本节的工具结果字符上限是两个不同限制，本节不涉及、数值不动；
- 对评测的影响（E1–E6 工具结果形态）列入《M3～M6 工程规格书 v0.2》§11 #23，M4 首轮评测观测。

具体配置项见 §10。

【事实】

```text

reassembly
rule engine

```

而不是重复实现成熟基础 parser。

# 6. PCAP / PCAPNG 输入层

## 6.1 PCAP

【事实】

经典 pcap savefile：

- 文件头 24 bytes；
- 每条 packet record header 16 bytes；
- 文件头魔数同时编码字节序与时间戳精度；
- snaplen 决定捕获数据是否可能被截断。

因此：

```text
reader
 ├─ endian
 ├─ timestamp precision
 ├─ snaplen
 └─ linktype
```

必须是 Reader 状态，而不是全局常量。

参考：

https://www.tcpdump.org/manpages/pcap-savefile.5.html

---

## 6.2 PCAPNG

【事实】

PCAPNG 使用 block 结构：

```text
Block Type
Block Total Length
Body
Block Total Length
```

SHB：

```text
0x0A0D0D0A
```

用于识别 Section Header Block。

其 Byte-Order Magic：

```text
0x1A2B3C4D
```

用于判断 section 字节序。

PCAPNG 可以：

- 多 section；
- 多 interface；
- 不同接口属性；
- 不同 timestamp resolution。

因此 Reader 必须维护：

```rust
SectionState {
    endian,
    interfaces,
}
```

而不是：

```rust
GlobalEndian
```

---

## 6.3 输入层状态机

```text
DetectFormat
   │
   ├── PCAP
   │      └── LegacyPcapReader
   │
   └── PCAPNG
          └── PcapNgReader
                 │
                 ├── SHB
                 ├── IDB
                 ├── EPB
                 ├── SPB
                 ├── NRB
                 └── ISB
```

未知 block：

```text
skip + counter++
```

不得：

```text
panic
```

```rust
    ethernet,

    decode_status,
}
```

---

## 7.1 Timestamp

【设计】

内部使用：

```text
integer nanoseconds + original precision metadata
```

JSON 序列化时使用字符串保存 canonical nanoseconds：

```json
{
  "ts_unix_ns": "1717689600123456789",
  "ts_precision": "ns"
}
```

这样避免 JavaScript `Number` 对大整数造成精度问题。

---

## 7.2 Payload Reference

不把大 Payload 直接塞入每一个 JSON event。

采用：

```json
{
  "payload_ref": {
    "packet_index": 1821,
    "offset": 54,
    "length": 438
  }
}
```

Rust 引擎可以通过原始 capture 再读取数据。

# 9. 协议解析矩阵

MVP：

| 协议 | 第一阶段 | 目标 |
|---|---:|---|
| Ethernet II | 必做 | EtherType / MAC |
| 802.1Q VLAN | 必做 | VLAN tag |
| ARP | 必做 | request/reply |
| IPv4 | 必做 | header / fragmentation |
| IPv6 | 必做 | header / extension chain |
| TCP | 必做 | header / flags / seq / ack |
| UDP | 必做 | header |
| ICMP | 必做 | type / code |
| ICMPv6 | 必做 | type / code |
| DNS | 必做 | query / response / counts |
| HTTP/1.1 | 必做 | request/status + headers |
| TLS | 必做 | metadata |
| DHCP | 必做 | message type + options |

明确不要求：

```text
完整协议语义
完整 MIME
完整 HTTP body parsing
TLS plaintext recovery
```

# 10. TCP 流重组

## 10.1 Session Key

MVP 使用规范化五元组：

```text
transport protocol
src IP
src port
dst IP
dst port
```

规范方向采用：

```text
endpoint A = lexical smaller endpoint
endpoint B = lexical larger endpoint
```

这样不会因为“谁先发包”而生成两套 session id。

---

## 10.2 Reassembly

每条流维护：

```text
next_seq
segments[]
missing_ranges[]
retransmissions
overlap_count
fin_seen
rst_seen
```

状态：

```text
NEW
ACTIVE
HALF_CLOSED
CLOSED
INCOMPLETE
```

---

## 10.3 重传

当收到：

```text
seq range already present
```

记录：

```text
retransmission = true
```

不重复向 Payload 输出。

---

## 10.4 乱序

例如：

```text
1000-1099
1200-1299
1100-1199
```

重组器应最终得到：

```text
1000-1299 contiguous
```

但如果中间永远缺失：

```text
missing 1100-1199
```

则流状态：

```text
INCOMPLETE
```

不能伪造完整 Payload。

---

## 10.5 资源上限

【设计】

```yaml
reassembly:
  max_stream_buffer: 8MiB
  stream_timeout: 60s
  max_sessions: 100000
  max_segments_per_stream: 4096
```

超过限制：

```text
drop oldest buffered segment / mark incomplete
```

具体替换策略在实现时固定，并加入单元测试。

# 12. 规则引擎

## 12.1 不再使用旧的自由文本 condition

旧设计：

```yaml
condition: |
  count(syn_without_ack, src_ip, window=10s) > 100
```

【废弃】

原因：

- 需要自己实现 expression parser；
- 错误消息不友好；
- 很难静态校验；
- 很难限制规则复杂度；
- 不利于测试。

---

## 12.2 当前 YAML DSL

```yaml
id: NET-TCP-SYN-BURST-001
version: 1

name: TCP SYN 突发检测
severity: high

scope: packet

match:
  protocol: tcp
  flags:
    contains: [SYN]
    excludes: [ACK]

threshold:
  metric: count
  group_by: [src_ip]
  window: 10s
  operator: gt
  value: 100

description: >
  单一源 IP 在时间窗口内产生大量未完成
  TCP SYN，可能存在扫描或 SYN Flood 特征。

tags:
  - tcp
  - dos
  - scan
```

---

## 12.3 原语

第一阶段只允许：

```text
count
distinct_count
sum_bytes
ratio
```

group_by：

```text
src_ip
dst_ip
src_port
dst_port
protocol
session
```

条件：

```text
gt
gte
lt
lte
eq
neq
```

窗口：

```text
1s
5s
10s
30s
1m
5m
```

不允许第一版规则执行任意代码。

# 13. 内置规则

## 13.1 SYN Burst

检测：

```text
SYN without ACK
group_by src_ip
within time window
```

输出：

```text
count
unique destination
completed handshakes
rst count
```

---

## 13.2 Port Sweep

候选条件：

```text
single source
→ same destination
→ many destination ports
→ short window
```

重点不是固定一个“攻击阈值”，而是提供结构化指标。

---

## 13.3 DNS Suspicious Behavior

第一阶段只做：

```text
query rate
average qname length
maximum label length
distinct queried domains
```

可选启发式：

```text
high entropy label
```

结果统一写成：

```text
possible_dns_tunnel
```

而不是：

```text
dns_tunnel_confirmed
```

---

## 13.4 Malformed Packet

来源：

```text
decoder error
length mismatch
invalid field relationship
truncated header
```

规则引擎只负责聚合这些错误。

# 15. Agent 分析策略

Agent 默认工作流：

```text
STEP 1
get_capture_summary

STEP 2
决定优先观察：
  protocol / conversation / alerts

STEP 3
获取 Top conversations

STEP 4
若发现异常：
  check_alerts
  filter_packets

STEP 5
只在必要时：
  inspect_packets
  reconstruct_stream

STEP 6
关联多个证据

STEP 7
输出 findings

STEP 8
生成报告
```

---

## 15.1 最大步骤

【设计】

```yaml
agent:
  max_steps: 12
  max_tool_calls: 20
  max_same_tool_calls: 5
```

Agent 连续两次得到同质化结果后：

```text
stop and summarize
```

防止：

```text
LLM
→ tool
→ tool
→ tool
→ tool
→ ...
```

无限循环。

---

## 15.2 不记录 Chain of Thought

【设计】

数据库只记录：

```text

input summary
result summary
duration
status
```

不要求保存模型的隐藏思维过程。

报告记录：

```text

```

而不是：

```text
chain of thought
```

例：

```text

2. top conversations showed abnormal fan-out
3. SYN burst rule matched source 192.168.1.105
4. packet inspection confirmed many SYN without ACK
```

# 21. IPC：Rust Engine ↔ Python Agent

## 21.1 采用 JSONL

【设计】

不做：

```text

```

作为第一版接口。

采用：

```text
Rust worker process
```

原因：

1. Rust / Python 完全解耦；
2. 不需要处理跨语言 ABI；
3. 调试时可以直接观察 JSON；

5. 很适合课程项目展示“模块化架构”。

# 33. 当前明确的 ADR

## ADR-001：不做 Rust ↔ Python FFI

【设计】

选择：

```text
JSONL over stdin/stdout
```

而不是：

```text
PyO3
```

原因：降低初期复杂度、便于调试、边界清晰。

未来性能有实际问题再换 IPC。

---

## ADR-002：采用 `pcap-parser + etherparse`

【设计】

不从头实现整个 PCAP/协议解析栈。

自研核心：

```text
Packet model
aggregation
reassembly
rules
query
```

---

## ADR-003：Agent 使用当前 LangChain agent API

【设计】

代码依赖：

```python
from langchain.agents import create_agent
```

而不是已经 deprecated 的：

```python
from langgraph.prebuilt import create_react_agent
```

ReAct 作为设计思想存在，而不是把某个旧 API 写进架构契约。

---

## ADR-004：SQLite first

【设计】

课程项目默认：

```text
SQLite
```

PostgreSQL 通过 repository abstraction 支持。

---

## ADR-005：结构化 YAML DSL

【设计】

规则不允许自由执行表达式或任意代码。

---

## ADR-006：Agent 不直接访问任意 SQL

【设计】

Agent 只能调用 typed query tools。

开发者才可以使用独立的只读 SQL 调试接口。

---

## ADR-007：不保存 Chain of Thought

【设计】

保存：

```text
tool trace
evidence
findings
```

不把模型隐藏推理当作产品数据。

# 34. 当前风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| PCAPNG corner cases | 高 | 使用成熟 parser + golden tests |
| TCP 重组复杂 | 高 | 明确 bounded reassembly |
| LLM 幻觉 | 高 | evidence-first |
| Tool loop | 中 | step / call limit |
| Payload 敏感信息 | 高 | redact + bounded payload |
| 数据库膨胀 | 中 | 不默认存完整 Payload |
| 规则误报 | 中 | basis + evidence + 不宣称确定攻击 |
| LangChain API 变化 | 中 | Agent API 封装在 `agent/` |
| PostgreSQL 方言差异 | 中 | repository layer |
| 项目范围膨胀 | 高 | MVP 明确排除项 |

# 37. 最终验收标准

一个可用于课程展示的 v0.2，至少满足：

```text
✓ 可以打开 PCAP / PCAPNG
✓ 可以解析核心协议
✓ 可以生成稳定的 session
✓ 可以处理 TCP retransmission / out-of-order
✓ 可以执行 YAML rules
✓ 可以输出 alerts
✓ Python Agent 可以调用 Rust tools
✓ Agent 会根据前一步结果决定下一步工具
✓ 报告里的数字来自工具结果
✓ Finding 有 evidence
✓ 坏包不会让整个任务 panic
✓ 有自动化测试
✓ 有至少一组 benchmark
✓ README 可以指导第三方启动
```

# 38. 项目完成后的“演示主线”

建议最终演示不要从“输入一个 pcap，然后 LLM 突然输出一份报告”开始。

而是展示：

```text
① 打开 PCAP
      ↓
② Rust 统计协议
      ↓
③ 找到 Top sessions
      ↓
④ 规则发现 SYN burst
      ↓
⑤ Agent 看到告警
      ↓
⑥ Agent 主动过滤相关包
      ↓
⑦ Agent 再检查一个 TCP session
      ↓
⑧ 关联证据
      ↓
⑨ 输出 Finding
      ↓
⑩ 生成最终报告
```

这样才能把项目中“协议分析”和“Agent”两个部分同时展示出来。

# 39. 开发原则总结

PacketSage 的设计核心只有三句话：

> **Rust 负责把网络流量变成可靠的结构化证据。**

> **Agent 负责决定下一步应该寻找什么证据。**

> **报告负责把结论、证据和局限性一起交给人。**

只要这三条不被破坏，未来增加 Web UI、更多协议、更多规则或更多模型，都只是外围能力扩展，而不会改变项目核心架构。
